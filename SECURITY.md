# Security Policy

## Reporting a vulnerability

Please do not open a public issue for a security problem.

Use GitHub's private reporting instead: go to
**Security → Report a vulnerability** on this repository. If that is
unavailable, open a public issue that contains only a one-line description
("security report, please open a private channel") and no technical detail.

Include, where you can:

- the affected endpoint, file, or feature
- steps to reproduce
- the impact you believe it has

You can expect an acknowledgement within a few days. Fixes ship in a normal
commit, and the reporter is credited in the advisory unless they ask not to be.

## What counts as a vulnerability

- Authentication or authorisation bypass
- Exposure of secrets, tokens, or password material
- Injection, or a way to read or modify another user's data
- A way to reach an admin-only action as a lesser role

## What is out of scope

- Missing hardening headers on the development server
- Rate-limit tuning, or denial of service through deliberate flooding
- Anything requiring an already-compromised server or database
- Reports with no demonstrated impact, generated by scanners alone

## Handling credentials

There is no sign-up flow: accounts are created with the `user:create` CLI
script. To provision an account:

```bash
npm --prefix backend run user:create -- someone@example.org "a-strong-password" --role=STAFF
```

Roles are `ADMIN`, `STAFF`, and `VIEWER`. `ADMIN` can create other accounts and
is the only role that can manage them. `STAFF` can create and edit charity
records. `VIEWER` is read-only.

Never commit a `.env` file. It is git-ignored, and `backend/.env.example`
holds placeholders only. Rotate `JWT_SECRET` if it is ever exposed: doing so
invalidates every issued token, and users sign in again.
